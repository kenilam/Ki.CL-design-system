Cascade layers decide which rule wins when two rules set the same property on the same element. Every stylesheet in the design system and in the host goes into one of seven layers, so the layer decides first, and load order and selector length only settle a tie inside a layer.

## Why we use them

Without layers, CSS settles a tie between two rules by specificity, then by which stylesheet came last. Both are fragile here, for three reasons.

**Load order isn't stable.** The site is two builds on one page: the host and the design system remote, loaded through Module Federation. In development, Vite injects one `<style>` per module in import order, and `core/styles` lost ties with a component's own styles. A production build splits CSS by chunk and links each chunk's dependencies first, and there the same `core/styles` won them. The same source gave opposite results. The bug that showed it: in the built site only, `.kicl-layout` beat the logo's own styles, set it to `min-block-size: 100dvb`, and pushed it out of its header.

**Specificity keeps rising.** To win a tie, a rule needs a longer selector. The utilities used to repeat their own class name (`.kicl-x.kicl-x`) for exactly that, and each fix like it raises the bar for the next rule that has to win.

**Some rules always have to win.** A class on an element, like `kicl-padding-wide`, should beat the component it's on. A view should be able to restyle a component. A vendor reset should never override the design system. None of that could be promised by specificity alone without `!important` everywhere.

Layers solve all three by deciding the winner by layer first. Load order and selector length only matter inside a layer, so a component can't beat a utility with a longer selector or a later load, and the order is the same in development, in production and in any host.

## How layers work

A cascade layer is a named group of rules, made with the CSS `@layer` at-rule. When two declarations compete, the browser compares their layers before it looks at specificity or source order. A rule in a later layer wins over a rule in an earlier one, even when the earlier rule has the more specific selector.

```css
@layer components, utilities;

@layer components {
  /* Two classes, but in the earlier layer */
  .kicl--components--card.kicl--components--card--size--sm {
    padding: var(--kicl--components--card--spacing);
  }
}

@layer utilities {
  /* One class, in the later layer, so it wins */
  .kicl-padding-wide {
    padding: var(--kicl-gutter-wide);
  }
}
```

Three more rules from the spec matter here:

- **Order is set by the first `@layer` statement the browser sees.** Naming a layer again later doesn't move it.
- **Styles outside any layer beat every layer.** A stray unlayered stylesheet would win over the whole design system, which is why even the vendor resets are put in a layer.
- **`!important` reverses the order.** An important declaration in an earlier layer beats an important one in a later layer. So `!important` is for a rule that has to beat everything after it, and isn't a way to win a fight between two utilities.

The definitions are in [CSS Cascading and Inheritance Level 5, Cascade Layers](https://www.w3.org/TR/css-cascade-5/#layering), and MDN has a readable reference at [@layer](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer).

## The seven layers

Lowest first. Each layer beats every layer above it in this list.

1. **`reset`** holds the vendor resets, `normalize.css` and `reset-css`. `core/styles/reset.css` imports them with `@import ... layer(reset)`, since leaving them unlayered would put them above everything.
2. **`base`** holds element defaults: `body`, headings, form controls, focus rings and the theme classes (`styles.body.scss`, `styles.generic.scss`, `styles.headings.scss`).
3. **`layout`** holds `.kicl-layout`. It sits below `components` because `Layout` clones its classes onto the child it wraps, and the child component's own styles should win.
4. **`components`** holds every component's stylesheet, and the docs pages' own styles.
5. **`wrappers`** holds the components that put their class on a child, `Animation` and `Frame`. They sit above `components` so the wrapper's styles win over the child's.
6. **`views`** holds a host's page styles. Every stylesheet in Ki.CL goes here, and so do the design system's status pages. A view can restyle any component without raising specificity.
7. **`utilities`** holds every `kicl-*` class and the `:root` tokens in `core/styles`. A class you put on an element wins over component and view styles, so `className='kicl-padding-wide'` on a Card works without `!important`.

## How a stylesheet gets its layer

Component and view stylesheets don't write `@layer` themselves. At build time, `getStyleLayer` in `Design/scripts/get-style-layer.ts` picks the layer from the file's path, and the Vite config wraps the compiled CSS in it. Each file also gets the full `@layer reset, base, layout, components, wrappers, views, utilities;` statement at the top, so whichever stylesheet loads first fixes the order, and no file has to be guaranteed to load first.

- `core/styles/styles.body.scss`, `styles.generic.scss` and `styles.headings.scss` go to `base`.
- `core/styles/layout.scss` goes to `layout`.
- Every other file in `core/styles` goes to `utilities`.
- `status/` goes to `views`.
- `components/animation/` and `components/frame/` go to `wrappers`.
- Everything else goes to `components`.
- Sass partials, whose names start with `_`, are left unwrapped, because a layer would scope their mixins and functions to that block.

The host does the same in `App/.client/helper/get-style-layer.ts`, and puts every stylesheet it compiles in `views`.

## Why the list is written twice

The host and the design system ship separate stylesheets onto one page, and the first `@layer` statement the browser reads sets the order for both. If the two lists ever differed, which one won would depend on which file loaded first. So `LAYERS` in the design system's `Design/scripts/get-style-layer.ts` and in Ki.CL's `App/.client/helper/get-style-layer.ts` must stay identical, and changing one means changing the other in the same release.

## When you write CSS

- **In a view,** write plain selectors. They're already above every component.
- **In a component,** don't raise specificity to beat another component. If one has to win, it belongs in a different layer.
- **On an element,** use a utility class. It wins over both.
- **Only use `!important`** for a rule that has to beat every later layer. Two rules use it today: the 16px floor on iOS fields in `base`, which has to stay above any `kicl-font-size-*` class, and `Animation` hiding an element that has left, which has to beat a display class on the same element.
